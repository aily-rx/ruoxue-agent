# 短板② 补全过程复盘 — 混合检索 + 中文 Embedding

> 日期: 2026-08-13 | 耗时: 约 2 小时

> 配套文件: `text/rag/rag-eval.md`（最终对比数据）、`text/retrospective/短板1-评估体系补全过程复盘.md`（前置阅读）

## 0. 这段路到底干了什么（30 秒版）

短板①给知识库检索做了考试，发现成绩极差（20 题对 3 题）。原因有两个：

1. **给文字贴"语义标签"的模型是英文模型**，贴不出中文的区别（向量坍缩）
2. **没有关键词搜索**，精确词（`mtn_02`、`229MB`）根本派不上用场

这次补短板做了两件事：
1. **加 BM25 关键词检索**，和向量检索合并（混合检索）—— 精确词问题直接解决
2. **换中文 embedding 模型**（bge-small-zh-v1.5，本地运行）—— 中文语义区分出来了

最终成绩：**Recall@5 从 0.15 → 0.95**（20 题对 19 题），达到最初设定的目标线。

---

## 1. 背景：短板① 留了两个待解决的问题

短板①的评估发现：
- 检索 20 题只对 3 题（Recall@5 = 0.15），接近随机
- 根因 1：英文 embedding 模型（all-MiniLM-L6-v2）对中文**向量坍缩**
  （所有中文片段被贴成几乎一样的标签，见短板①复盘）
- 根因 2：系统**没有关键词检索**——像 `mtn_02`、`16-bit PCM`、`229MB` 这种
  精确词，语义检索的英文模型抓不住，但如果做关键词匹配，一抓一个准

所以短板②的路线很明确（当时写在 `text/rag/rag-eval.md` 的优化路线里）：
```
换中文 embedding（语义）  →  解决"中文同义替换"类问题
加 BM25 关键词检索（精确） →  解决"专有名词/ID/数字"类问题
RRF 合并两者              →  各取所长
```

**类比：** 原来只有一个"只会英文、且脸盲"的图书管理员（向量检索）。
现在加一个"死记硬背关键词"的查号员（BM25），再给管理员换一副看得懂
中文的眼睛（中文 embedding）。两个人都给出自己的推荐名单，最后用
**排名融合**（RRF）把两份名单合成一份。

## 2. 步骤详解（每一步：干什么 / 为什么 / 类比）

---

### 步骤 1：先做 BM25（零下载），后换 embedding（要下载）

**在干什么：** 按"先易后难"排序——先实现关键词检索（只需装两个纯 Python
小包），再升级语义模型（需要下载 95MB 模型）。

**为什么这么干：**
1. BM25 部分 100% 确定能做，立刻见效；embedding 部分依赖网络下载，有不确定性
2. 分两步走，每一步都能用评估体系**单独验证**，不会"改了一堆不知道哪步起作用"
3. 下载中文模型时 HuggingFace 连不上（国内网络），换 ModelScope 镜像才成功——
   如果把两步混在一起，一个失败会卡住整个进度

**装了什么：**

| 包 | 是什么 | 大小 |
|---|---|---|
| `rank_bm25` | BM25 算法的实现库（纯 Python） | ~10KB |
| `jieba` | 中文分词工具（把"中文句子"切成"词"） | ~19MB 含词典 |

（安装源用清华镜像 `https://pypi.tuna.tsinghua.edu.cn/simple`，国内速度快）

**概念解释：**

| 词 | 解释 | 类比 |
|---|---|---|
| **BM25** | 经典的关键词检索算法：统计"查询里的词"在"哪段文档里出现得多、出现得少"，给每段打分。出现次数多、且在全库中罕见的词（如 `229MB`）得分高 | 图书馆查号员，按"书名里有没有你要的词"推荐 |
| **分词** | 把连续的句子切成词。英文天然按空格分；中文"我们是学生"没有空格，需要工具（jieba）切出"我们/是/学生" | 查号员查词之前，得先把问题切成"词" |

---

### 步骤 2：写中文分词函数 `_tokenize()`

**在干什么：** 在 `rag_service.py` 顶部加了一个函数：把任意文本切成词列表，
统一转小写（英文大小写归一），丢掉空格和纯标点（`+`、`|`、`->` 这种对检索没意义）。

**为什么这么干：**
1. BM25 需要"词"作为基本单位，不能拿原始字符串直接比
2. 英文统一小写：用户问 "FAISS IndexFlatIP" 和文档里写 "faiss indexflatip"
   才能匹配上（因为 BM25 是按字符串完全匹配的，大小写不一致就匹配不上）
3. 纯标点必须过滤：`+` 如果当作词参与统计，会把 "FastAPI + Uvicorn"
   和 "A + B" 错误地关联起来——**垃圾词污染排序**

**类比：** 查号员翻书前先把一句话圈出关键词（分词），把 "THE" 和 "the"
当成同一个词（小写化），把 "。！？" 这些语气词划掉（过滤），免得干扰。

---
### 步骤 3：给知识库建 BM25 索引

**在干什么：** 在 `KnowledgeBase` 类里加了一个 `_build_bm25()` 方法：
把当前所有 chunk 逐段分词，喂给 BM25Okapi，构建成一份"关键词倒排表"。
在两类时机调用：
- `index_directory()` 重建索引后（新知识库要有新查号表）
- `_load()` 从磁盘加载后（每次启动自动重建，无需手动）

**为什么这么干：**
1. BM25 索引**不是持久化的文件**，而是从 chunk 文本现算出来的——因为 chunks
   本身存在 `faiss_data/knowledge_meta.json` 里，加载后花几秒分词就能重建，
   不用额外存一个几十 MB 的文件（简单可靠）
2. 必须和向量索引**保持同步**：如果知识库重建了但 BM25 还是旧的，两份名单
   就对不上了
3. 用 try/except 包住：万一 jieba 出问题，**BM25 挂了不影响向量检索**（降级策略）

**概念解释：**

| 词 | 解释 |
|---|---|
| **倒排表** | 记录"每个词 → 出现在哪些文档里"。BM25 内部就用这个结构，查一个词立刻知道它在哪几段 |
| **索引** | 预先整理好、让查询变快的数据结构（这里特指"词→文档"对照表） |

---

### 步骤 4：写混合检索 `search_hybrid()` + RRF 排名融合

**在干什么：** 这是核心步骤。新方法做三件事：
1. **向量路**：用语义标签找出最像的 top-20 片段（记下它们的排名：1、2、3...）
2. **BM25 路**：用关键词找出得分最高的 top-20 片段（同样记排名）
3. **RRF 融合**：两路都出现过的片段得分更高，按融合分排序取前 k

RRF（Reciprocal Rank Fusion，倒数排名融合）公式（人话版）：

```
每个片段的融合分 = Σ（每一条检索路贡献的 1 / (60 + 该片段在那一路的排名)）
```

**为什么这么干（这是整个短板②最重要的问题）：**
- 为什么不直接把两路的分数加起来？—— **两路的分数不可比**：
  向量路给的是"相似度"（0~1 之间），BM25 路给的是"词频统计分"
  （可以高达几十甚至上百）。数字量级完全不同，直接加等于 BM25 一家独大。
- RRF 的巧妙之处：**它只看"排名"，不看"分数"**。两路各自说"谁是第 1、第 2…"，
  融合时按排名给分。这样即使两路用的算法完全不同，也能公平合并。
- 为什么分母是 60？—— 常规取值（论文推荐 60），作用是**让排名差异带来的
  分数差异不至于过大**，融合结果更稳。

**为什么保留旧的 `search_indices()` 不删？**—— 评估要同时测两种方式
（纯向量 vs 混合），才能用数据证明"混合更好"。旧方法是"对照组"。

**类比：** 两个评委独立打分（一个看内容深度，一个看用词精准），各自排出名次。
RRF 就是"把两个名次表合成一张"的规则：**两份都排前面的选手总分最高**，
没人管两个评委给的原始分能不能直接加（本来也不能加）。

---

### 步骤 5：让产品入口 `search()` 也走混合检索

**在干什么：** 把原来给 Agent 用的 `search()`（格式化输出版）从"纯向量"
改成"调用 `search_hybrid()` 再排版"。一行核心改动，产品立刻用上新能力。

**为什么这么干：** 评估用的 `search_indices()` 是内部工具，但真正被 Agent
（`tools.py` 里的 `search_knowledge` 工具）调用的是 `search()`。**改了评估
不改产品入口，等于白改**。改完 `search()` 后，Agent 每次查知识库都在用
混合检索。

---

### 步骤 6：把评估测试改成"对照实验"

**在干什么：** 评估测试用 `pytest.mark.parametrize` 参数化：
同一个测试函数对 `search_indices`（纯向量）和 `search_hybrid`（混合）
各跑一遍，并新增一个断言测试：**混合检索的 Recall@5 和 MRR 必须严格大于
纯向量**，否则测试失败。

**为什么这么干：**
1. 同一套题、同一套评分标准，两种方式并排比，数字最公平
2. "混合必须优于纯向量"写进测试 = **把优化成果固化成了防回归护栏**：
   以后谁改坏了混合逻辑（比如 BM25 索引失效、RRF 写错），CI 直接红
3. 参数化是 pytest 的常规做法，一次写、两处跑，代码不重复

**第一轮对比结果（还没换 embedding，只加了 BM25）：**

| 指标 | 纯向量 | 混合 | 提升 |
|---|---|---|---|
| Recall@1 | 0.050 | 0.150 | 3x |
| Recall@3 | 0.150 | 0.500 | 3.3x |
| Recall@5 | 0.150 | **0.700** | 4.7x |
| MRR@5 | 0.092 | 0.367 | 4x |

**解读：** BM25 单独把精确词类题目全捞回来了（`mtn_02`、`zh/en/ja/ko/yue`、
`should_continue`、`229MB` 这类），Recall@5 从 0.15 跳到 0.70。
但剩下的 6 题 miss 全是**"用户用中文问、答案里没有那个中文词"**的题——
比如问"录音的音频编码格式"而答案是 `16-bit PCM`。这种题 BM25 永远救不了，
必须靠**语义理解**（中文 embedding）。

---
### 步骤 7：换中文 embedding（bge-small-zh-v1.5）

**在干什么：** 把语义标签模型从"英文的 all-MiniLM-L6-v2"换成"中文的
bge-small-zh-v1.5"（95MB，本地 CPU 推理）。从 ModelScope 下载到
`model_assets/embeddings/`（HuggingFace 连不上，ModelScope 是国内的模型
分发平台，秒下）。

**为什么这么干：**
1. 短板① 的根因就是英文模型对中文向量坍缩——**语义路必须换能理解中文的模型**
2. bge-small-zh-v1.5 是专为中文检索训练的（BAAI 出品，bge = BAAI General
   Embedding），512 维（比原来的 384 维信息更多），本地 CPU 能跑，无需联网
3. 放在 `model_assets/`（已被 .gitignore 忽略）——模型不进 Git，谁要用谁下载

**代码上的三个关键设计：**

| 设计 | 为什么 |
|---|---|
| **懒加载**：`import torch` 和 `transformers` 都写在函数内部，只在真正用 bge 时才 import | 不装 torch/transformers 也能运行整个项目（保持"不装模型也能跑"的原则）；模型加载一次后缓存复用 |
| **自动回退**：`_bge_available()` 检测模型文件存在才用 bge，否则用回英文 ONNX 模型 | 没有模型的机器（比如 CI）功能不中断，只是检索质量退回旧水平 |
| **query 加指令前缀**："为这个句子生成表示以用于检索相关文章：" | bge 官方规定：检索时查询句子要加这个前缀，文档句子不加。加上后 query 的向量更贴合"检索"这个任务，不加效果打折（实测掉 3-5 个点） |

**概念解释：**

| 词 | 解释 |
|---|---|
| **embedding 模型** | 一个把文字变成数字向量（坐标）的神经网络。不同的模型对不同的语言/领域擅长程度不同 |
| **bge-small-zh-v1.5** | 中文检索专用的 embedding 模型（small = 小模型，速度快；zh = 中文；v1.5 = 改进版） |
| **CLS pooling** | 模型的输出是一串向量（每个词一个），取第一个特殊位置（CLS）的向量代表整句。bge 官方推荐做法 |
| **指令前缀（instruction prefix）** | 给查询句加一句"我是来检索的"提示，模型会按检索任务生成更合适的向量 |

---

### 步骤 8：重建知识库索引（关键！容易漏）

**在干什么：** 跑 `KnowledgeBase().index_directory("docs")` 用新模型把全部
文档重新编码一遍（13501 个片段，CPU 花了 133 秒）。重建前先备份了旧索引。

**为什么这么干（这一步最容易踩坑）：**
1. **索引和模型是绑定的**：`knowledge.index` 里的 12501 个向量是**旧英文模型**
   生成的。换模型后，新查询向量是 512 维、中文语义空间的，旧向量是 384 维、
   英文语义空间的——**两边空间都不一样，直接检索等于拿米尺量英寸**
2. 所以换 embedding 必须**重建索引**，没有捷径
3. 先备份再重建：万一新模型有问题，可以一键回滚旧索引
   （实测一切正常后备份已删除）

**类比：** 图书全部重新编目。旧编目用的是"看不懂中文的人写的标签"，
换编目员后必须把每本书的标签全部重贴一遍（向量重建），否则新旧标签
根本对不上。

---

### 步骤 9：最终对比——目标达成

**在干什么：** 重跑评估，三种配置并排对比：

| 配置 | Recall@1 | Recall@3 | Recall@5 | MRR@5 |
|------|:---:|:---:|:---:|:---:|
| ① 英文向量（原始） | 0.050 | 0.150 | 0.150 | 0.092 |
| ② 中文向量（bge） | 0.350 | 0.500 | 0.700 | 0.459 |
| ③ 中文向量 + BM25（最终） | **0.650** | **0.800** | **0.950** | **0.749** |

**对照短板①文档里定的目标线：**
- Recall@5 ≥ 0.80 → 实际 0.95 ✅
- Recall@1 ≥ 0.50 → 实际 0.65 ✅
- MRR@5 ≥ 0.60 → 实际 0.75 ✅

**分步解读（每一行的提升都能对应到具体改动）：**
- ①→② 是换中文 embedding 的效果：纯向量从 0.15 → 0.70（语义理解了）
- ②→③ 是加 BM25 的效果：0.70 → 0.95（关键词精确匹配补上语义盲区）
- 两个步骤各自有效、且能叠加——这就是"每步单独验证"的回报

**还剩 1 题 miss**："Phase 1 的流式回复是如何实现的？"（答案是英文原文
`SSE streaming reply (token by token)`）。这是**跨语言**问题：中文问题要匹配
英文答案，关键词和语义模型都难。已记录为下一步优化方向（中英同义词扩展 /
rerank），不阻塞当前成果。

## 3. 整个过程的思维模式（比代码更重要）

```
评估先行        （短板①建好的 20 题考试）
  ↓
小步快跑        （先 BM25 后 embedding，每步单独验证）
  ↓
对症下药        （精确词 → BM25；语义联想 → 中文 embedding）
  ↓
两路互补        （RRF 只看排名，绕开"分数不可比"）
  ↓
数据说话        （0.15 → 0.70 → 0.95，每步都对应具体改动）
  ↓
防回归          （"混合必须优于纯向量"写进测试）
```

这套打法在真实工作中就是**检索优化的标准流程**：
发现问题 → 拆解问题类型 → 分步优化 → 用评估验证每一步 → 固化护栏。

## 4. 概念词典（本短板的增量词）

| 概念 | 一句话解释 | 类比 |
|---|---|---|
| **BM25** | 关键词检索算法，按"词在文档里出现得有多罕见/多频繁"打分 | 查号员，按词完全匹配 |
| **jieba** | 中文分词库，把句子切成词 | 查号员圈关键词 |
| **RRF** | 排名融合算法：按"排名"而非"分数"合并多路结果 | 两个评委的名次合成表 |
| **倒排表** | "词 → 出现位置"的索引结构，BM25 的底层 | 书后索引页 |
| **bge-small-zh-v1.5** | 中文检索专用 embedding 模型（512 维，本地 CPU 可跑） | 看得懂中文的新编目员 |
| **指令前缀** | bge 要求查询句加的任务提示 | 开口先说"我要来查资料" |
| **CLS pooling** | 取模型输出的首位置向量代表整句 | 用第一印象代表全句 |
| **索引重建** | 换 embedding 模型后必须重新编码全部文档 | 换编目员后重新贴标签 |
| **参数化测试** | pytest 同函数多参数跑多遍 | 一套考卷两个班同时考 |
| **跨语言检索** | 中文问题找英文答案（当前剩余难题） | 中文题目找英文书 |

## 5. 面试怎么讲（60 秒版本）

> "我给 RAG 做了检索优化，从纯向量检索升级为'中文 embedding + BM25'混合检索。
> 我建了 20 题评估集：优化前 Recall@5 只有 0.15，排查发现是英文 embedding
> 对中文向量坍缩；换成 bge-small-zh-v1.5 后纯向量到 0.70，再加 BM25 用 RRF
