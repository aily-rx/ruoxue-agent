## 0. 这段路到底干了什么（30 秒版）

给项目的"知识库检索"（RAG 的 R 部分）**做了一次考试**：

1. 出了 20 道题（问法 → 标准答案）
2. 让检索系统去答
3. 统计成绩：**20 题只对了 3 题（15%）**
4. 追查原因：**负责给中文打标签的模型是英文模型，中文内容它根本分不清**
5. 把成绩和原因写成文档，作为以后每次优化的"对比基准"

**核心收获：发现了"检索一直是坏的"这个隐藏了很久的问题。**
在没有评估体系之前，这个项目从来不知道自己检索效果有多差。

## 1. 背景：为什么要做评估体系

### 问题在哪

RAG（检索增强生成）是"先找资料，再让 AI 根据资料回答"。**找资料这一步叫"检索"（Retrieval）**。
我们项目的检索流程是：

```
用户提问
   ↓
把提问转换成"语义标签"（embedding）
   ↓
用标签在知识库里找出最像的几段文字（向量检索）
   ↓
把找到的文字交给 LLM，让它参考着回答
```

问题在于：**没有人验证过"找出来的几段文字是不是真的对"**。之前全靠肉眼感觉
"好像找得还行"。而 AI 应用的输出不是固定的，同样的提问每次结果都可能不同，
**靠感觉是管理不了不确定性的**——这就是为什么必须用数字说话。

### 类比：像给 AI 的"记忆"做一次考试

知识库就像图书馆，检索系统是图书管理员。以前管理员每次递书，我们只看他递得快不快
（接口响应快），**从没检查过他递的书对不对**。这次我们出的 20 道题就是抽查：
每道题问一个具体问题（"Live2D 白块问题怎么修？"），看管理员能不能从图书馆里
**准确找到**记载答案的那本书那一页。考试分数就是量化指标。

### 为什么说这个短板的优先级是 P0

面试时面试官必问："**你怎么证明你的 RAG 效果好？**"
- 没有评估：只能答"我试了试，感觉还行" → 面试官判定你没有工程思维
- 有评估：能答"我建了 20 题评估集，Recall@5 是 0.15，发现 embedding 模型是英文的，
  换中文模型 + BM25 混合后升到 0.95" → 有数据、有排查、有优化，这是完整的故事

## 2. 步骤详解（每一步：干什么 / 为什么 / 类比）

---

### 步骤 1：先认识自己的知识库

**在干什么：** 打开 `faiss_data/knowledge_meta.json`，统计里有什么。
得到：26 份文档（docs 技术方案、PRD、踩坑记录），切成了 **12501 个片段**。

**为什么这么干：** 评估的"题目"必须从真实存在的资料里出。如果知识库里根本没有
这个内容，检索答不出来也不能怪它——题目超纲不算。**先摸清题库范围，再出题。**

**顺带发现：** 每个文档恰好 500 个片段——说明分块代码里有个 500 片上限（`max_chunks=500`），
长文档可能被截断了。这个记下来，以后可能是个优化点。

**类比：** 出考卷前先看教材目录，确认考的都是教材里有的内容。

**概念解释：**

| 词 | 解释 |
|---|---|
| **chunk（片段）** | 把一份长文档切成的小段（本项目每段约 500 字，相邻两段有 80 字重叠）。因为 LLM 和向量模型一次只能处理有限长度的文本，所以要把长文档切块 |
| **faiss_data** | FAISS 向量索引的存储目录。FAISS 是 Facebook 开源的"高维向量搜索库"，知识库构建好后，检索就靠它 |
| **元数据（metadata）** | 记录每个片段"从哪份文档、第几段切出来的"的附加信息，存在 `knowledge_meta.json` 里，方便溯源 |

---

### 步骤 2：给检索加一个"返回原始结果"的方法

**在干什么：** 在 `backend/agent/rag_service.py` 的 `KnowledgeBase` 类里新增了
`search_indices(query, k)` 方法，返回 `[(片段编号, 相似度), ...]`。

**为什么这么干：** 原来唯一的检索方法 `search()` 返回的是**排版好的文字**
（给用户看的那种），里面混着格式、标题、截断。要算"对不对"的指标，需要知道
**命中的是第几个片段**——原始的编号和分数。改源码前先读了原文件（遵守
read-before-code 原则），确认 `search()` 的返回结构后再加方法。

**类比：** `search()` 是"把书递给你"（包装好的），`search_indices()` 是
"告诉你这本书在书架第几排第几格"（原始坐标）。考试评分需要的是坐标。

**注意：** 这个新方法**后面还有用**——做混合检索（BM25 + 向量）时，要把两路结果
按"片段编号"合并排序，没有编号就合不了。所以这步不是白干。

---

### 步骤 3：出 20 道题（评估数据集）

**在干什么：** 新建 `backend/tests/eval/dataset.py`，写 20 个样本，每个样本是
一对：`问题（用户会怎么问）+ fragment（标准答案的原文片段）`。例如：

```python
{
    "question": "Live2D 模型渲染出现白色矩形覆盖部件是什么原因？",
    "fragment": "NoPremultipliedAlpha is not allowed",
}
```

**为什么这么干：**
1. **问题必须口语化**——用户不会问"请检索 premultiplied alpha 相关文档"，
   而是"白块咋回事"。口语问法更能测出检索的真实水平。
2. **fragment 必须短且独特**——用知识库原文里的一句话作为"标准答案"，
   测试时只要检索结果里包含这段原文，就算答对。
3. 为什么用"原文片段"而不是"片段编号"？——知识库可能重建，编号会变，
   但**原文不会变**。用内容定位答案，测试永远跟得上真实数据。
4. 写完先跑一个校验脚本：**逐个确认 20 个 fragment 都能在知识库里找到**。
   有一个写错了（把 `工具调用**: DeepSeek-V3` 写成了单冒号），被校验脚本当场抓住。

**类比：** 出考卷 = 把"教材里的一句话"改写成"用户会问的问题"。
校验 = 确认每道题的答案确实在教材里，防止出超纲题。

---
### 步骤 4：写评分程序（评估测试）

**在干什么：** 新建 `backend/tests/eval/test_rag_retrieval.py`，写了一个测试函数：
对 20 道题逐个做检索，然后算 4 个分数：**Recall@1 / Recall@3 / Recall@5 / MRR@5**。

**为什么这么干：**
1. 用 pytest 写而不是随手脚本——测试会自动进 CI 的 pytest 管道，以后
   每次改动检索代码，测试自动重跑，**防止悄悄改坏了没人知道**（回归保护）。
2. 一次算多个指标而不是只看"对不对"——"对不对"（Recall）只回答"找没找到"，
   还需要知道"排第几"（MRR）。因为 RAG 通常只把**前几名**交给 LLM，
   排第 5 和排第 50 差别巨大：排第 5 的能用，排第 50 的等于没找到。

**概念解释（评分标准）：**

| 指标 | 白话解释 | 计算公式（人话版） |
|---|---|---|
| **Recall@k** | 20 道题里，标准答案出现在"检索结果前 k 名"中的比例 | 答对题数 ÷ 总题数 |
| **Recall@1** | 标准答案恰好排第一的比例（最严格） | 同上，k=1 |
| **Recall@5** | 标准答案排在检索结果前 5 名里的比例（RAG 常用 k=5，因为一般只取 5 段喂给 LLM） | 同上，k=5 |
| **MRR@5** | 平均倒数排名。答案排第 1 得 1 分，排第 2 得 1/2，排第 5 得 1/5，没找到得 0 | 所有题的得分之和 ÷ 题数 |

MRR 为什么看"倒数"：排第 1 比排第 5 好 5 倍，倒数排名能惩罚"排得很靠后"的情况，
比单纯数"对了几题"更细腻。

**还有一个细节：** 测试文件顶部写了 `skipif`——如果 `faiss_data/` 不存在（被
.gitignore 忽略，CI 上不会构建），就**跳过而不是报错**。因为知识库是本地生成的
大文件，不该进 Git；CI 上没知识库，跳过评估、继续跑别的测试，两边都绿。

**类比：** 这是"阅卷程序"。交卷后自动算分，分数打进档案（日志），
以后每次优化完重新阅卷对比。

---

### 步骤 5：首次跑分——成绩惨不忍睹

**在干什么：** 运行测试，得到第一份真实成绩单：

| 指标 | 分数 |
|---|---|
| Recall@1 | **0.050**（20 题只有 1 题排第一） |
| Recall@3 | **0.150**（3 题进前 3） |
| Recall@5 | **0.150**（3 题进前 5） |
| MRR@5 | **0.092**（平均排名约第 11 名） |

**为什么在意：** 这是项目的**第一个量化检索指标**。0.15 的 Recall@5 意味着
"喂给 LLM 的 5 段资料，有 85% 的概率跟问题无关"——**LLM 相当于在拿无关材料回答**。
之前所有"感觉检索还行"的判断，被数据推翻了。

**关键心法：数字差不可怕，没有数字才可怕。** 差 → 有优化空间 → 优化后数字上升 →
这就是简历上"把 Recall@5 从 0.15 提升到 X"的来源。有了基线，后面每步改动都能
验证是不是真的变好了。

---

### 步骤 6：排查——是"评分太严"还是"检索真差"

**在干什么：** 写了一个临时调试脚本，做**对照实验**：
- 第一轮（评估测试）：结果带了 0.3 的相似度过滤（低于 0.3 的结果被丢弃）
- 第二轮（调试脚本）：**去掉过滤**，直接看原始排名和分数

**为什么这么干：** 检索结果差有两种可能，必须先分清是哪种，否则会修错地方：
1. **可能性 A：分数线（阈值）太高** —— 答案其实找到了，但分数低于 0.3 被扔掉了
2. **可能性 B：排名本身就不对** —— 正确答案从头到尾没进过前几名

如果是 A，把阈值调低就行；如果是 B，调阈值没用，得换模型/换检索方式。
**这个"先区分问题类型，再对症下药"的排查思路，比修好问题本身更重要。**

**结果：** 所有问题的相似度都高达 0.45~0.77（远超 0.3），但答案就是不在前 5 名。
→ **是 B：排名错了，不是阈值误杀。**

**概念解释：**

| 词 | 解释 |
|---|---|
| **相似度（cosine similarity）** | 两个"语义标签"有多像的分数，0~1，越高越像。检索就是把问题标签和所有片段标签比一遍，取最高的几个 |
| **阈值（threshold）** | 分数线。本项目设定相似度低于 0.3 的结果直接丢弃，防止把完全不相关的碎片交给 LLM |
| **对照实验** | 只改变一个条件（去掉过滤），其他都不变，对比两次结果来定位原因 |

---

### 步骤 7：揪出真凶——英文模型给中文"打标签"彻底失败

**在干什么：** 再看调试脚本的原始分数，发现一个反常现象：
**同一道题的 top-3 结果相似度一模一样（0.539 / 0.539 / 0.539），而且三次返回的是同一个片段。**
顺着这条线索查到 `rag_service.py` 里用的 embedding 模型：
`chromadb` 的默认 `DefaultEmbeddingFunction`，底层是 **all-MiniLM-L6-v2——纯英文模型**。

**为什么这就是根因：** embedding 模型的工作是"把文字变成一串数字（向量）"，
让"意思相近的文字数字也相近"。**all-MiniLM-L6-v2 只在英文上训练过**，
对中文基本是"看天书"：它把几乎所有中文片段都映射到了几乎相同的数字区域
（这叫**向量坍缩**）。于是：
- 所有中文片段的"标签"长得都差不多 → 谁跟问题"最像"基本靠运气 → 排名接近随机
- 相似度都挤在 0.5~0.7 之间，区分不开 → 所以出现了"5 个结果分数全一样"的怪象

**类比：** 让一个只会英语的人给中文图书编目。他把每本书的"摘要"都翻译成
"看不懂的符号"，结果每本书的标签看起来都一样。之后有人来查"讲 Live2D 白块的
书"，管理员只能瞎猜——因为编目本身就是坏的。**问题不在查书，在编目。**

**概念解释：**

| 词 | 解释 |
|---|---|
| **embedding（嵌入/语义向量）** | 把文字转换成一串数字（如 384 维向量）。设计目标是：语义相近的文字，数字距离也近 |
| **向量** | 一串数字（比如 [0.12, -0.35, 0.88, ...]），可以理解为"文字在多维空间里的坐标" |
| **向量坍缩** | 本应各不相同的向量变得几乎一样。常见于"模型没学过这种语言/领域"，导致所有输入都落到相近坐标 |
| **维度（dim）** | 向量的长度。384 维意味着每个文字被映射到 384 维空间的一个点 |

**这条线索的完整推理链（面试可以直接讲）：**
```
成绩差（Recall@5=0.15）
  → 阈值不是原因（分数都 0.5+）
  → 排名错（正确答案不在前 5）
  → 奇怪现象：top-3 分数完全相同
  → 查 embedding 模型 → all-MiniLM-L6-v2 是英文模型
  → 根因：英文模型对中文向量坍缩
```

### 步骤 8：固化成果——基线文档 + 回归保护

**在干什么：** 做了三件事：
1. 把评估代码提交到 `backend/tests/eval/`（数据集 + 测试，可重复运行）
2. 写 `text/rag/rag-eval.md`：基线数字、根因分析、优化路线（换中文 embedding →
   BM25 混合检索 → rerank）、目标验收线（Recall@5 ≥ 0.80）
3. 全量验证：评估测试 PASSED + 原有 11 个测试 PASSED + ruff 无错误

**为什么这么干：**
1. **可复现**：别人（未来的你）跑一条命令就能复现这份成绩单
2. **可对比**：基线文档是"原点的照片"，下一步换模型后重跑评估，
   数字一对比就知道有没有变好（**用数据驱动优化，而不是感觉驱动**）
3. **防回归**：评估测试进了 pytest 管道，以后谁改了检索逻辑把成绩改差了，CI 直接变红

**类比：** 手术前先拍 X 光片存档。之后每次治疗（优化）再拍一张，
两张对比，看得见有没有好转，而且机器（CI）自动提醒你复查。

## 3. 整个过程的思维模式（比代码更重要）

这次补短板，真正的价值不是 20 行测试代码，而是这条**可迁移的思维链**：

```
1. 定义问题     "检索好不好" 不能用感觉衡量 → 先定义指标（Recall@k / MRR）
2. 建立测量     出题（数据集）→ 写阅卷程序（测试）→ 跑出基线（数字）
3. 基于数据决策  数字差 → 不急着改代码，先做对照实验定位"为什么差"
4. 定位根因     顺着反常现象（分数全相同）追到模型层（英文模型）
5. 固化与对比   基线文档存档 → 优化后重测对比 → 防止回归
```

这套流程在 AI 应用开发里**通用**：RAG 要评估、Prompt 要评估、Agent 要评估。
你简历上写"建立了 RAG 评估基线"，面试官追问的其实就是这条思维链能不能讲通。

## 4. 概念词典（按出现顺序速查）

| 概念 | 一句话解释 | 类比 |
|---|---|---|
| **RAG** | Retrieval-Augmented Generation：先检索资料，再让 LLM 基于资料回答 | 开卷考试，先翻书再答题 |
| **chunk（片段）** | 长文档切出的小段，是检索的基本单位 | 书的章节片段 |
| **embedding** | 文字 → 一串数字（语义坐标）的转换 | 给文字贴"语义标签" |
| **向量** | 一串数字，代表文字在多维空间的位置 | 坐标 |
| **向量坍缩** | 不同文字却得到几乎相同的向量 | 所有书被贴成一样的标签 |
| **向量检索** | 找"标签最像"的几段文字 | 拿着问题标签去图书系统查最像的 |
| **相似度** | 两个标签有多像（0~1），检索排序依据 | 匹配度分数 |
| **阈值** | 分数线，低于就丢弃 | 查到的资料太离谱直接扔掉 |
| **FAISS** | 开源的高效向量搜索库，本项目用它存索引、做查询 | 图书馆的索引卡片系统 |
| **Recall@k** | 标准答案进前 k 名的比例 | 考试答对率（前 k 名算对） |
| **MRR** | 平均倒数排名，惩罚"找到了但排太靠后" | 阅卷时第一名满分、第二名减半 |
| **基线（baseline）** | 优化前的原始成绩，用于对比 | 健身前的体测数据 |
| **回归保护** | 测试自动重跑，防止改动把已有功能改坏 | 每次体检都做同一套项目 |

## 5. 下一步（接短板②：让检索变好）

基线已经证明"检索是坏的"，根因是**英文 embedding 模型**。下一步按
`text/rag/rag-eval.md` 的优化路线走：

1. **换中文 embedding 模型**（如 `bge-small-zh-v1.5`，本地 ONNX，512 维）
   —— 让中文语义标签真正区分开，这是 Recall 翻倍的根基
2. **加 BM25 关键词检索**（jieba 分词）与向量检索**混合**（RRF 合并）
   —— 精确词（`mtn_02`、`16-bit PCM`、`229MB`）用关键词一抓一个准
3. **每步重跑本评估**，对照 `text/rag/rag-eval.md` 的目标线（Recall@5 ≥ 0.80）验收

到时候这份文档就是"优化前的体检报告"，新成绩单和它并排一放，故事就完整了。
