> 日期: 2026-08-14 | 耗时: 约 2 小时

## 0. 这段路到底干了什么（30 秒版）

把 Agent 链路从"黑盒 print()"升级成"可追溯的 JSON 日志"：

1. **JSONFormatter 升级**：原来只输出固定的 4 个字段（时间/级别/来源/消息），现在**支持 extra 自定义字段**——`request_id`、`duration_ms`、`tool_calls` 都能进 JSON
2. **Agent 链路埋点**：`run_agent_stream` 的每个阶段（请求开始 / Chroma 检索 / skill 匹配 / 请求完成）都输出一条 JSON 日志，**带耗时**
3. **request_id 贯穿**：每个请求一个 id，从响应头 `X-Request-Id` 返回给前端，所有日志都带它——**按 id 过滤就能拼出一次请求的完整链路**
4. **重试留痕**：LLM 调用重试时打 WARNING 日志（第几次重试、失败原因）

验证结果：**92 个测试全绿，行覆盖率 77% → 79%**（`agent_graph.py` 92%、`config.py` 98%）。

**核心收获：中间产物必须留痕，否则 AI 应用不可调。** 之前排查问题只能靠"感觉"，现在能精确说出"这次回答慢是检索慢了 2 秒，还是 LLM 推理慢了 5 秒"。

## 1. 背景：为什么 AI 应用必须"留痕"

### 问题在哪

补之前，Agent 链路的"日志"长这样：

```python
print(f"[Chroma] retrieved context ({len(chroma_hits)} chars)")
print(f"[Skill] matched '{skill_name}' for input: ...")
```

而 `config.py` 里**早就写好了** `JSONFormatter` 和 `setup_logging()`——`main.py` 启动时也调用了——**但 Agent 链路一行都没用上**。基础设施建好了，没人走。

为什么这是大问题？**AI 应用和传统后端的排查差异**：
- 传统后端：报错了有堆栈，改一行代码就修好
- AI 应用：LLM 输出不稳定，回答错了可能是**检索的问题、prompt 的问题、模型的问题、工具的问题**——四选一，而且每个都"看起来没报错"。没有中间产物日志，就只能靠猜

### 类比：给航班装黑匣子

之前像一架没有黑匣子的飞机：飞得好不好全靠乘客口碑（"感觉还行"），出了事查不出原因。装上黑匣子（阶段日志）后：每一个环节（起飞/巡航/降落）都有记录（耗时、结果），**出事能定位到具体环节**。

### 为什么说这个短板的优先级是 P1

1. **面试必问**："Agent 回答错了，你怎么排查是 LLM 的问题、检索的问题还是工具的问题？"——有 tracing 你能拿出"每条请求的完整链路日志"，没有就只能说"我看看代码"
2. **短板④ 的容错也依赖它**：容错让"失败时不崩"，可观测性让"失败时能查"——两个缺一个，容错就是白做的
3. 日志结构化 → 可索引 → 可告警，这是工程意识的直接体现

## 2. 步骤详解（每一步：干什么 / 为什么 / 类比）

---

### 步骤 1：先读现状——发现"基础设施已建好，没人走"

**在干什么：** 读 `main.py`、`config.py`、`agent_graph.py`，盘点可观测性现状。

**发现：**
- `main.py` 已调用 `setup_logging()`（JSONFormatter 已装到 root logger）✅
- `config.py` 的 `JSONFormatter` 只输出固定 4 字段（timestamp/level/logger/message）——**带不了 request_id 和耗时**
- `agent_graph.py` 全是 `print()`，且**没有 request_id 概念**

**结论：** 要做的不是"搭日志系统"（已搭好），而是：
1. 升级 Formatter 支持 extra 字段
2. 给 Agent 链路接上 logger + 埋点
3. 引入 request_id 贯穿

**类比：** 房子装了电表箱（setup_logging）但屋里没布线（没人用 logger），这次是把线路接到每个房间。

---

### 步骤 2：升级 JSONFormatter——让"追踪字段"进得去 JSON

**在干什么：** 改造 `config.py` 的 `JSONFormatter.format()`：

```python
# 输出固定字段
payload = {"timestamp": ..., "level": ..., "logger": ..., "message": ...}

# 附加 extra 自定义字段（request_id / duration_ms / skill 等）
for key, value in record.__dict__.items():
    if key in payload or key in _STD_ATTRS or key.startswith("_"):
        continue
    try:
        json.dumps(value)
    except (TypeError, ValueError):
        value = str(value)
    payload[key] = value
```

核心思路：`logger.info("msg", extra={"request_id": "abc"})` 时，logging 会把 `request_id` 变成 record 的属性——遍历 `record.__dict__` 把**非标准属性**（排除 `name/msg/args/levelname` 等 22 个标准字段）全部带进 JSON。

**为什么这么干：**
1. 不这样改，`request_id` 就永远进不了日志——而它是 tracing 的**主键**，Docker 部署时 Loki/ELK 就是按它过滤的
2. 遍历 `__dict__` 而不是写死字段——以后加任何追踪字段（`skill_name`、`attempt`）都自动进 JSON，**不需要再改 Formatter**
3. 不可序列化的值（比如某个对象）转字符串兜底，**绝不让一条日志因为字段问题炸掉**

**类比：** 原来快递单只有 4 个固定栏目；现在改成"附加信息"自由填写——贴什么标签（request_id）都能扫进去。

---

### 步骤 3：Agent 链路埋点——每阶段一条 JSON 日志

**在干什么：** `run_agent_stream` 加 `request_id` 参数 + 四个阶段埋点：

| 埋点 | 字段 | 回答什么问题 |
|---|---|---|
| `agent request start` | request_id, user_text 摘要 | 这次请求问了什么 |
| `chroma retrieve` | request_id, **duration_ms**, hit_chars | 长期记忆检索快不快、有没有命中 |
| `skill match` | request_id, skill | 技能系统是否触发、触发了哪个 |
| `agent request done` | request_id, **duration_ms**, tool_calls, reply_chars | 全程耗时、调了几次工具、回了多少字 |

```python
_stage_ms = time.monotonic()
chroma_hits = chroma_memory.retrieve_context(user_text)
_logger.info(
    "chroma retrieve",
    extra={
        "request_id": rid,
        "duration_ms": round((time.monotonic() - _stage_ms) * 1000, 1),
        "hit_chars": len(chroma_hits),
    },
)
```

另外给短板④ 的 `_ainvoke_with_retry` 加了 `before_sleep` 回调——重试时打 WARNING 日志（第几次、失败原因）。

**为什么这么干：**
1. **每条日志带 request_id**——这是拼接链路的"订书钉"，没有它日志就是一堆孤儿
2. **耗时用 `time.monotonic()`**——不能用 `time.time()`（会受系统时钟跳变影响），monotonic 只增不减，测耗时是标准选择
3. **检索日志只记长度不记内容**（hit_chars 而不是全文）——避免日志膨胀，这是面试指南明确说的设计约束
4. 重试打 WARNING 而不是 INFO——**级别本身就是信号**，告警规则可以直接订阅"出现了 llm call retry"

**类比：** 每个安检口（阶段）都拍照记录（日志）并盖上同一枚邮戳（request_id），事后按邮戳把照片拼成一个人的完整行程。

---

### 步骤 4：routes 接入——request_id 从哪来、给谁看

**在干什么：** 两个小改动：
1. `chat` endpoint 入口生成 `request_id = uuid.uuid4().hex[:12]`，传给 `run_agent_stream(..., request_id=request_id)`，并放进响应头 `X-Request-Id`
2. `main.py` 的 CORS 加 `expose_headers=["X-Request-Id"]`——**不 expose 的话，浏览器里的前端 JS 读不到这个响应头**（跨域安全限制）

**为什么这么干：**
1. request_id 在**入口统一生成**——保证一次请求只有一个 id，谁都不许自己造
2. 响应头返回给前端——前端可以把 id 展示给用户（"工单号"）或用于后续排查
3. `uuid4().hex[:12]`——短且不泄露时间信息，日志里不占地方

**类比：** 医院挂号的"就诊号"——进门（入口）统一发号，之后的每个检查单（日志）都手写同一个号。

---

### 步骤 5：写测试——这次一次全过

**在干什么：** 两组测试：

**`test_observability.py`（8 个）：**
- JSONFormatter 3 个：extra 字段进 JSON / 标准字段恒在 / 不可序列化字段转字符串不炸
- 流式埋点 4 个：四阶段日志齐全 / **request_id 在所有日志中一致** / done 日志带 tool_calls 和 reply_chars / 不传 request_id 时自动生成且贯穿
- 重试日志 1 个：FlakyLLM 失败 1 次 → caplog 里有 `llm call retry` 且 attempt=1

**`test_routes.py` 扩展：** `/api/chat` 响应必须有 `X-Request-Id` 头。

关键技巧：pytest 的 **caplog fixture**——它自带 handler 捕获日志 record，`caplog.set_level(logging.INFO, logger="agent.agent_graph")` 指定只捞这个 logger，断言 `record.request_id`（extra 字段变成 record 属性，直接断言属性而不是解析文本）。

**结果：8 个全过，一次绿。**

**为什么这么干：**
1. **"request_id 在所有日志一致"是最重要的断言**——tracing 的根基就是 id 贯穿，断了 tracing 就废了
2. 断言 caplog 而不是去抓 stdout——JSONFormatter 只是输出格式，**测试验证的是"打了什么"，不是"打印得多好看"**
3. integration 测响应头——保证入口真的把 id 发给了前端

**类比：** 黑匣子装完不是看它"通电了"（格式正确），而是**模拟一次飞行，检查每个环节的录音都在、时间戳对得上**（caplog 断言）。

## 3. 整个过程的思维模式（比代码更重要）

```
先读现状      （setup_logging 已就绪——别重复造轮子, 只补缺失的）
  ↓
字段先行      （request_id 是主键, 一切日志围绕它设计）
  ↓
级别即信号    （INFO=正常阶段, WARNING=重试/异常, 可被告警订阅）
  ↓
格式不吞错    （不可序列化转字符串兜底, 日志绝不因字段炸掉）
  ↓
测试验证链路  （caplog 断言 request_id 贯穿, 而不是检查打印样式）
```

这套打法通用：**任何"多阶段、多依赖、输出不确定"的系统**（RAG 管线、Agent、多工具工作流）都需要"request_id + 阶段耗时 + 结果摘要"三件套日志。

## 4. 概念词典（按出现顺序速查）

| 概念 | 一句话解释 | 类比 |
|---|---|---|
| **结构化日志** | 每行是一个 JSON 对象（有字段名），可以被机器解析/索引/过滤 | 填好的表格 vs 一段流水账 |
| **JSONFormatter** | 把日志 record 序列化成 JSON 行的格式器 | 快递单打印机 |
| **extra 字段** | `logger.info(..., extra={"request_id": ...})` 附加的自定义字段 | 快递单上的备注栏 |
| **request_id** | 一次请求的唯一 id，贯穿所有日志 | 就诊号 / 工单号 |
| **埋点（instrumentation）** | 在代码各阶段插入日志/计时代码 | 给流水线装传感器 |
| **duration_ms** | 阶段耗时（毫秒），用 `time.monotonic()` 测量 | 秒表读数 |
| **tracing** | 把一次请求跨所有阶段串联起来的追踪能力 | 黑匣子 |
| **caplog** | pytest 内置的日志捕获 fixture，测试断言"打了什么日志" | 录音回放 |
| **expose_headers** | CORS 配置：允许浏览器 JS 读取指定响应头 | 把信件从门缝递出来 |
| **monotonic 时钟** | 只增不减的计时器，不受系统时间调整影响 | 秒表 vs 墙上的钟 |

## 5. 下一步（接短板⑥：并发、缓存与成本）

可观测性打通后，一个数据立刻有了意义：**日志里的 duration_ms 和 token 消耗**——这正是短板⑥ 成本优化的度量基础。

短板⑥ 的路线（详见 `text/interview/面试准备与项目补全指南.md`）：
1. **LLM client 单例**：`_build_llm()` 每次调用都新建 ChatOpenAI——改成模块级缓存，复用连接池
2. **embedding 结果缓存**：相同 query 不重复跑 embedding 推理（LRU）
3. **成本记账**：LLM 调用后读 `response.usage` 的 prompt_tokens / completion_tokens，累加到短板⑤ 的 JSON 日志——回答"一次对话多少钱"这个问题
