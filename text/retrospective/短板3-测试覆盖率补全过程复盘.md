## 0. 这段路到底干了什么（30 秒版）

给项目的"模型外围的确定性逻辑"补了一次系统性的测试覆盖：

1. 盘点现状：**Agent 核心逻辑（流式解析、技能匹配、分块、口型映射、记忆）一个测试都没有**
2. 写 5 组测试：mock 掉 LLM 和外部依赖，测"你自己的逻辑"，不测"模型的表现"
3. 第一次跑分：**59 过 2 挂**——挂的 2 个都是测试自己写错了（一个是重复建目录，一个是**没读实际代码就臆测了音素结构**）

**核心收获：测试不只是"验证代码没坏"，更是"逼你读懂自己的代码"。**
写测试的过程中，我发现自己对 `viseme_mapper` 的音素结构有错误记忆——是测试暴露了它。

## 1. 背景：为什么"AI 应用的测试"和普通项目不一样

### 问题在哪

补齐之前，项目的测试只有 3 个文件：
- `test_tools.py`（39 行，测工具函数）
- `test_routes.py`（58 行，测 API 路由）
- `tests/eval/`（短板① 新增的 RAG 检索评估）

而**最核心、最容易坏**的代码——`agent_graph.py` 的流式解析、`skill_loader.py` 的关键词匹配、`rag_service.py` 的分块逻辑、`viseme_mapper.py` 的口型映射、`chroma_memory.py` 的记忆读写——**全部没有测试**。

为什么这很危险？因为这些代码是"**确定性逻辑**"：LLM 的输出每次都不一样（不确定），但**处理 LLM 输出的代码是固定的**（确定）。比如"从流式文本里用正则提取 `[EMOTION: happy|0.8]` 标签"——这个逻辑 100% 确定，但它特别怕回归：**只要有人改了 prompt 格式或正则，整条链路立刻静默坏掉，而且没人发现**，因为 AI 应用没有"明显的错误"——它只是回答变得有点怪。

### 类比：给流水线的"传送带"上保险

LLM 是流水线上的工人（不可控，每次干活质量略有波动），而解析逻辑是传送带和质检台（机械、固定）。以前保险只给质检台上了（tools/routes 有测试），**传送带本身没人检查**——工人一换姿势（prompt 格式变了），传送带就把零件甩飞，但整条线看起来还在转。

### 为什么说这个短板的优先级是 P1

1. **面试必问**："你怎么保证 AI 应用不坏？"——答案就是：把模型外围的确定性逻辑全部单测覆盖，模型本身用标注样本评估（配合短板①的评估体系）。没有测试，这句话就是空话。
2. **CI 已经跑了 pytest**——测试太少显得 CI 是摆设，面试官一眼能看穿。
3. 补测试**不依赖任何外部服务**（不花 API 钱、不需要模型），是纯本地、纯确定性的收益。

## 2. 步骤详解（每一步：干什么 / 为什么 / 类比）

---

### 步骤 1：先读源码，摸清"被测对象"长什么样

**在干什么：** 写测试之前，先把 5 个要测的模块全部读了一遍：
- `agent_graph.py`：`run_agent_stream` 的完整逻辑——情绪标签正则、`tool_phase` 工具阶段抑制、事件产出顺序
- `emotional_agent.py`：`EMOTION_TAG_RE` 正则的精确定义、`SSEEvent` 结构
- `skill_loader.py`：`match()` 的计分公式（Σ关键词长度 × priority，阈值 10）、YAML 解析双路径
- `rag_service.py`：`_chunk_text` 的分块规则、`_tokenize` 的过滤规则、`KnowledgeBase` 的构造/持久化
- `viseme_mapper.py`：单元音 1 帧、复合韵母 2 帧、声母混合权重
- `chroma_memory.py`、`config.py`：构造参数、默认值

**为什么这么干：** 测试的断言必须来自**真实代码**，不是来自"我觉得它应该这样"。比如 `match()` 的阈值是 10、`chunk_size` 是 500、`overlap` 是 80——这些数字不读源码就写断言，等于拿猜的答案去考真实的系统。**先读后写这条铁律，写测试时同样适用。**

**类比：** 出考卷前先翻教材（源码），确认每道题的答案确实在教材里。

---

### 步骤 2：定测试策略——"模型外围全单测"

**在干什么：** 明确一个原则：**mock 掉 LLM 和所有外部依赖，测的是"你的逻辑"，不是"模型的表现"。** 具体手段：
- 流式解析测试：用一个 `FakeGraph` 替换模块级的 `agent_graph`，让它吐出**我们指定**的 chunk 序列（带标签的、不带标签的、带工具调用的）——就像用提词器给演员念台词，然后检查"导演的剪辑逻辑"对不对
- 记忆测试：`FakeChromaMemory` 返回空上下文，不碰真实 Chroma 数据库
- skill 测试：`FakeSkillLoader` 不读真实 skills 目录

**为什么这么干：**
1. 测试 LLM 的表现没有意义——它是外部模型，好坏由评估体系管（短板①），不由单测管
2. 真实依赖（网络、数据库、文件系统）会让测试**慢、脆、不可重复**——CI 上跑不了
3. 把外部依赖替换成假对象后，测试运行 <1 秒，且结果 100% 可复现

**类比：** 测试自动驾驶的"决策逻辑"时，你不会真的开车上路（外部依赖太多），而是在模拟器里喂各种路况录像（mock 输入），检查方向盘打没打对。

---

### 步骤 3：按"从易到难"写 5 组测试

**在干什么：** 按依赖复杂度排序逐个写：

| 顺序 | 测试文件 | 覆盖什么 | 为什么排在这 |
|---|---|---|---|
| 1 | `test_skill_loader.py` | 关键词匹配：命中/未命中/阈值/大小写/priority 加权/load/reload/最小 YAML 解析器 | 零外部依赖，纯函数，最快见效 |
| 2 | `test_viseme_mapper.py` | 音素→口型：1 帧/2 帧/鼻韵母收口/声母混合/时间轴/char_durations | 纯函数，但断言需要懂音素结构 |
| 3 | `test_rag_service.py` | 分块边界（短/空/超长/overlap/max_chunks）、临时库建库→检索→持久化→清空 | 模块级函数可单独测；`KnowledgeBase` 用 `tmp_path` 隔离 |
| 4 | `test_chroma_memory.py` | 写入/语义检索命中/无关排除/跨实例持久化 | 需要临时目录，但 API 简单 |
| 5 | `test_agent_stream.py` | 流式解析：情绪标签（单/跨 chunk）、默认 neutral、工具阶段抑制、done 收尾 | **最复杂**：要 mock 掉整个编译后的 LangGraph，放最后 |

**两个关键设计：**

1. **测试隔离用 `tmp_path` 而不是全局单例**——`chroma_memory.py` 和 `rag_service.py` 都有模块级全局单例（`chroma_memory = ChromaMemory()`、`knowledge_base = KnowledgeBase()`）。如果测试碰它们，就会读写真实的 `chroma_data/` 和 `faiss_data/`（还有可能被 gitignore 的模型）。正确做法：**直接实例化** `ChromaMemory(persist_dir=str(tmp_path))`，每个测试一个临时目录，测完自动清理。

2. **mock 编译后的图而不是 mock 函数**——`run_agent_stream` 直接调模块级全局 `agent_graph.astream(...)`。与其 patch 内部函数（要猜 LangGraph 内部结构），不如**替换整个 `agent_graph` 对象**：
```python
class FakeGraph:
    def __init__(self, items): self._items = items
    async def astream(self, inputs, stream_mode="messages"):
        for item in self._items: yield item

monkeypatch.setattr("backend.agent.agent_graph.agent_graph", FakeGraph(items))
```
这样 chunk 序列完全受控——想测"跨 chunk 被截断的情绪标签"，就喂 `["[EMOTION: sad|0.5] 我", "很难过"]` 两段，断言解析器能跨 chunk 累积识别。

**类比：** 组装测试的"作战沙盘"——每个外部角色（LLM、记忆、技能）都换成可控的演员，导演（被测函数）在台上演，我们只看他的决策对不对。

### 步骤 4：第一次跑分——59 过 2 挂，挂的全是测试自己写错

**在干什么：** 运行测试，得到第一份成绩单：**59 passed, 2 failed**。两个失败都不是被测代码的 bug，而是**测试代码自己的 bug**：

**失败 1：重复建目录（FileExistsError）**
`test_reload_picks_up_changes` 里先通过 `_loader(tmp_path)` 建了一次临时 skills 目录，又在同一个 `tmp_path` 下调用 `_make_skills_dir(tmp_path)` 建第二次——第二次 `mkdir` 撞上已存在的目录，直接炸。修复：第一次建目录时保存返回值，之后复用。

**失败 2（更有价值）：没读实际代码就臆测了音素结构**
`test_char_durations_override_uniform` 断言"你好"用 `char_durations=[100, 200]` 时时间轴终点是 300ms。我的推算："你"和"好"都是双元音各 2 帧 → 100/2×2 + 200/2×2 = 300。**实际是 200ms**——因为"你"(ni) 的韵母 `i` 是**单元音，只有 1 帧**（100ms），"好"(hao) 的韵母 `ao` 才是双元音 2 帧（200/2×2）。总时长确实是 300ms，但**最后一帧的起点是 200ms**（帧时间轴 [0, 100, 200]）。

**为什么在意：** 我写断言时凭的是"印象里的音素表"，而不是 `viseme_mapper.py` 里真实的 `_frames_for_final()` 分支。**测试断言和产品代码一样，不凭猜测——先读再写。** 这条铁律我用在了"测什么"上，却差点在"怎么断言"上违反。

**类比：** 裁判（测试）自己看错了规则书（源码），把运动员（被测代码）的合法动作判成犯规。检查的是裁判，不是运动员。

### 步骤 5：全量回归 + 覆盖率量化

**在干什么：** 三件事：
1. 跑全量测试（含原有的 integration 和 eval 评估）：**69 passed**（原 13 + 新 56）
2. 装 `pytest-cov` 跑覆盖率，得到数字：

| 模块 | 覆盖率 |
|---|---|
| `agent_graph.py`（流式解析） | **89%**（此前 0%） |
| `skill_loader.py`（技能匹配） | **93%** |
| `rag_service.py`（分块+检索） | **86%** |
| `chroma_memory.py`（长期记忆） | **86%** |
| `viseme_mapper.py`（口型映射） | **85%** |
| **TOTAL** | **74%**（目标 50%+） |

3. ruff 检查 + 提交（pre-commit 的 tdd/read-before/codebase hooks 全过）

**为什么这么干：**
1. **覆盖率是给"测试测试"的指标**——它告诉你"还有哪些代码没被验证过"，防止"测了但等于没测"（比如只测了快乐路径）
2. 74% 远超 50% 目标，但**不是 100% 才是好**——剩下未覆盖的恰好是三类**不该由单测覆盖**的东西：外部依赖型模块（`tools.py` 要 mock 网络、`asr_service.py` 要 ONNX 模型、`tts_service.py` 要 Edge TTS）、Legacy 代码（`emotional_agent.py`）、入口文件（`main.py`/`routes.py` 由集成测试覆盖）。**覆盖率是工具不是 KPI，关键是未覆盖的行你要能说出"为什么没覆盖"。**

**类比：** 覆盖率像体检的"检查项目清单"——不是项目越多越好，而是**每一项没查的，你都要说得出理由**。

## 3. 整个过程的思维模式（比代码更重要）

```
先读后写      （断言来自源码，不来自印象）
  ↓
确定性优先    （模型外围的逻辑才值得单测, 模型本身交给评估体系）
  ↓
外部依赖 mock （FakeGraph 替换整张图, tmp_path 隔离全局单例）
  ↓
测试也会错    （2 个失败都是测试自己的 bug——"你好"的韵母结构臆测错了）
  ↓
量化收尾      （覆盖率 74% + 未覆盖行能说清原因）
  ↓
固化防回归    （56 个新测试进 pytest 管道, 以后改解析逻辑 CI 自动把关）
```

这套打法对 AI 应用工程是**通用方法论**：LLM 不可测 → 把"围绕模型的控制逻辑"全部变成可测的确定性代码 → 用 mock 隔离一切不确定 → 用覆盖率看漏洞。

## 4. 概念词典（按出现顺序速查）

| 概念 | 一句话解释 | 类比 |
|---|---|---|
| **单元测试（unit test）** | 测单个函数/类的行为，不碰外部依赖 | 单独检查传送带上的一个齿轮 |
| **集成测试（integration test）** | 测模块之间真实协作（本项目的 test_routes.py） | 整条流水线试运行 |
| **mock / stub / fake** | 用假对象替换真实依赖，让输入完全可控 | 提词器 / 替身演员 |
| **monkeypatch** | pytest 的运行时替换机制：临时把模块全局换成假的 | 拍戏时临时换角，拍完换回来 |
| **fixture（tmp_path）** | pytest 提供的临时目录，每个测试独立、自动清理 | 一次性草稿纸 |
| **断言（assert）** | 测试的"判卷标准"，错了测试就红 | 裁判的哨子 |
| **覆盖率（coverage）** | 被测代码行数 ÷ 总行数，量化"测了多少" | 体检检查项目清单 |
| **确定性逻辑** | 相同输入必得相同输出的代码（正则、循环、映射）——最适合单测 | 传送带（机械的） |
| **黄金样例测试** | 用一份标注好的输入→期望输出做回归（本项目 RAG 评估集即此思路） | 标准答案库 |

## 5. 下一步（接短板④：错误处理与容错）

覆盖率报告里暴露了下一个靶子：**`tools.py` 只有 15%**——它的工具函数要 mock 网络（Tavily/wttr.in）才能测，而这正好是短板④"工具级容错"要动的代码。

短板④ 的路线（详见 `text/interview/面试准备与项目补全指南.md`）：
1. **循环失控防护**：LangGraph State 加 `tool_rounds` 计数器，超 5 轮强制 END——防止 Agent 陷入无限工具循环
2. **LLM 调用重试**：用 `tenacity`（已装）包指数退避重试，网络抖动自动恢复
3. **错误文案防幻觉**：工具失败返回"不要编造"指令，防止 LLM 幻觉补全
4. **read_file 大小上限**：防止读超大文件卡死

到时候这份文档里的"mock 外部依赖"手法会直接复用——给 `search_web` 挂假 Tavily 客户端，断言"失败时返回结构化错误串"。
