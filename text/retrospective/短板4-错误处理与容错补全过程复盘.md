> 日期: 2026-08-14 | 耗时: 约 2.5 小时
> 读者对象: 初学者（第一次接触"给 Agent 做容错"的人）
> 配套文件: `backend/agent/agent_graph.py`、`backend/agent/tools.py`、`backend/tests/unit/test_agent_robustness.py`、`backend/tests/unit/test_tools.py`

---

## 0. 这段路到底干了什么（30 秒版）

给 Agent 的四类"失败路径"补上了防护：

1. **循环失控防护**：LangGraph State 加 `tool_rounds` 计数器，agent 节点最多执行 5 轮，超限强制 END——**Agent 再也陷不进无限调工具的循环**
2. **LLM 调用重试**：`tenacity` 指数退避（3 次尝试），网络抖动/限流自动恢复，3 次耗尽原样抛出
3. **防幻觉文案**：三个外部依赖工具（搜索/天气/知识库）失败时，返回带"**不要编造**"指令的结构化错误——防止 LLM 用幻觉补全糊弄用户
4. **read_file 大小上限**：超过 5MB 拒绝读取——防止读超大文件卡死链路

验证结果：**84 个测试全绿，行覆盖率 74% → 77%**（`tools.py` 从 15% → 32%，`agent_graph.py` 91%）。

**核心收获：写"容错测试"又犯了三个测试自己的错误**——断言了字符串 `"END"` 而实际值是 `"__end__"`、async 函数测试忘了 `await`、mock 流里漏放 `ToolMessage` 导致被测逻辑被"误伤"。测试写错和产品写错一样要挨打。

## 1. 背景：为什么"考虑失败路径"是 Agent 工程的分水岭

### 问题在哪

补之前，Agent 的失败处理是"裸奔"的：

| 失败场景 | 之前的后果 |
|---|---|
| LLM 调用网络抖动/限流 | 直接抛异常 → 整条 SSE 流中断，用户看到 error 事件 |
| Agent 反复调工具停不下来 | **无限循环**：LLM 说"我再查一下"，工具返回，LLM 又说"我再查一下"……直到 API 超时 |
| 搜索/天气服务挂了 | 返回裸错误串 `Search error: xxx`——LLM 可能**编造一个搜索结果**来"完成任务" |
| 用户让读一个 10GB 文件 | `read_text()` 把内存吃满，进程卡死 |

为什么这对 AI 应用尤其致命？因为普通后端"失败了就是 500"，用户看得见；而 **Agent 失败时 LLM 倾向于"假装成功"**——工具坏了它不会说"我查不到"，它会编一个"查到了"。**幻觉补全是 AI 应用特有的失败模式，必须靠错误文案里的显式指令压住。**

### 类比：给"爱逞强的员工"配安全网

LLM 像一个**爱逞强的员工**：任务完不成时，第一反应不是报告，而是硬编一个结果交差。给他配安全网：
- 工作循环设上限（防他原地打转一整天）——循环上限
- 电话打不通自动重拨 3 次——LLM 重试
- 供应商垮了，明确告诉他"就说实话，不许编"——防幻觉文案
- 超大件货物不硬扛，直接拒收——文件大小上限

### 为什么说这个短板的优先级是 P1

1. **面试必问**："工具调用失败了怎么办？模型循环调用工具停不下来怎么办？"——这是 Agent 工程的核心问题。之前代码没有任何答案，现在每层都有答案 + 测试。
2. 真实场景中网络抖动、API 限流、工具报错是**常态**，没有容错的 Agent 就是 demo。
3. "考虑失败路径"是应届生稀缺的工程素养，**四层防护每层都能讲出设计理由**。

## 2. 步骤详解（每一步：干什么 / 为什么 / 类比）

---

### 步骤 1：先读源码，盘点"已有的"和"缺的"

**在干什么：** 读 `tools.py` 和 `agent_graph.py` 全文（先读后写），盘点容错现状。

**发现：** 文档（面试指南）写的"现状"已经过时——**工具级容错其实已经有了**：
- 5 个工具全部有 `try/except`，失败返回错误字符串而不是抛异常
- `get_weather` 已有 10s 超时（`timeout=10.0`）
- `read_file` 已有 8000 字符截断

**真正缺的是四件事：**
1. 错误文案是裸的（`Search error: xxx`）——**没有防幻觉指令**
2. `read_file` 没有**字节大小上限**（截断发生在读完之后，大文件在读之前就卡死了）
3. `agent_graph.py` 没有**工具循环上限**——`should_continue` 只看"有没有 tool_calls"，不看"调了多少次"
4. LLM 调用**没有重试**——一次网络抖动就整条链路失败

**类比：** 检查房子先看哪堵墙已经加固过（工具 try/except），别重复施工；真正要补的是地基（循环上限）和警报器（防幻觉）。

---

### 步骤 2：第一层——错误文案升级：结构化 + 防幻觉

**在干什么：** 三个外部依赖工具（`search_web` / `get_weather` / `search_knowledge`）的错误返回从：

```python
return f"Search error: {e}"                          # 旧: 裸错误
```

改成：

```python
return (
    f"[工具执行失败] search_web 出错：{e}。"
    "请告知用户网络暂时不可用，不要编造搜索结果。"   # 新: 结构化 + 防幻觉
)
```

**为什么这么干：**
1. **"[工具执行失败]" 前缀**是给 LLM 的"信号灯"——让它知道这是失败结果，不是正常数据
2. **"不要编造" 指令**是给 LLM 的"紧箍咒"——外部服务失败时它只有两个选择：如实告知或编造。没有指令时它会倾向编造（幻觉补全是 LLM 的默认倾向）
3. 错误返回后 **LLM 自己决定怎么办**（告知用户/换工具/换问法），而不是后端直接挂掉——这是"错误信息让 LLM 决策"的设计哲学

**类比：** 供应商（工具）交货失败时，采购员（LLM）默认会编个"货到了"。现在供应商的失败单上写着"**不许编**"——采购员只能如实上报。

---

### 步骤 3：第二层——read_file 大小上限

**在干什么：** 模块常量 + 读取前检查：

```python
MAX_FILE_SIZE_BYTES = 5 * 1024 * 1024  # 5 MB

# read_file 里, 在 read_text() 之前:
if filepath.stat().st_size > MAX_FILE_SIZE_BYTES:
    return f"Error: 文件超过 {MAX_FILE_SIZE_BYTES // 1024 // 1024}MB 上限，拒绝读取: {path}"
```

**为什么这么干：** 原有的 8000 字符截断是**读完之后**才生效——如果用户让读一个 10GB 文件，`read_text()` 会先把整个文件读进内存，**在读的那一刻就卡死了**，截断根本来不及。字节检查必须在读取**之前**。

**类比：** 原来是在"吃完了 10GB"之后说"你吃太多了"；现在是在动筷子之前就称重拒收。

---

### 步骤 4：第三层——循环失控防护（核心）

**在干什么：** 三处改动：

1. **State 加计数器**：
```python
class AgentState(TypedDict):
    ...
    tool_rounds: int  # agent 节点执行轮数, 超限强制 END 防无限工具循环

MAX_TOOL_ROUNDS = 5
```

2. **agent 节点每执行一次 +1**：
```python
response = await _ainvoke_with_retry(llm_with_tools, messages)
rounds = state.get("tool_rounds", 0) + 1
return {"messages": [response], "tool_rounds": rounds}
```

3. **路由检查超限**：
```python
def should_continue(state: AgentState) -> str:
    if state.get("tool_rounds", 0) > MAX_TOOL_ROUNDS:
        return END
    last_msg = state["messages"][-1]
    if hasattr(last_msg, "tool_calls") and last_msg.tool_calls:
        return "tools"
    return END
```

4. **超限提示用户**（`run_agent_stream`）：循环被强制终止且没有任何回复时，不是沉默，而是明确告知：
```
"抱歉，这个任务需要反复调用工具的步骤太多，我已经尽力了。请换一个更简单的问法，或者把任务拆小一点再试。"
```

**为什么这么干：**
1. 无限工具循环是 Agent 最经典的失控模式——LLM 被"再查一次"自我强化，LangGraph 官方文档的标准做法就是 **State 计数器 + 条件边检查**
2. 计数器放在 agent 节点递增（每轮必执行），路由处检查——**谁都不依赖"最后一次消息长什么样"**
3. 超限提示是"防御性输出"：宁可告诉用户"我尽力了"，也不能让用户面对一个没有回复的空流

**类比：** 电话客服的"每通电话限时 10 分钟"——不是为了不让客服干活，而是防止极端情况下的无限占线；超时后不是挂断，而是说"建议您换个方式咨询"。

---

### 步骤 5：第四层——LLM 调用重试

**在干什么：** 用 tenacity（依赖早已在 requirements 里，这次只是"用起来"）包装 LLM 调用：

```python
@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, max=10),
    reraise=True,
)
async def _ainvoke_with_retry(llm, messages) -> BaseMessage:
    """LLM 调用带指数退避重试（网络抖动/限流自动恢复, 3 次后原样抛出）。"""
    return await llm.ainvoke(messages)
```

`agent_node` 里原来的 `llm_with_tools.ainvoke(messages)` 换成 `_ainvoke_with_retry(llm_with_tools, messages)`。

**为什么这么干：**
1. **指数退避**（1s → 2s → 4s…）而不是固定间隔——限流场景下"等一会儿再试"成功率远高于"立刻猛试"
2. **`reraise=True`**：3 次耗尽后把最后一次异常**原样抛出**（不吞异常）——routes.py 会把它包装成 SSE error 事件，用户能看到"服务出错了"而不是"永远转圈"
3. 重试只包 `ainvoke` 不包整个节点——**工具执行不重试**（工具失败走错误文案路径），重试只针对"调用 LLM 这个网络动作"

**类比：** 打不通电话不是挂断重拨一次就放弃——拨 3 次，间隔逐渐拉长；3 次都不通就如实告诉用户"电话打不通"，而不是假装问到了。

---

### 步骤 6：写测试——又栽了三个"测试自己的错误"

**在干什么：** 写两组测试：
- `test_agent_robustness.py`（9 个）：`should_continue` 超限/未超限/无工具调用、`agent_node` 轮数递增 + 走重试包装、`_ainvoke_with_retry` 重试成功/耗尽抛错、`run_agent_stream` 超限提示/正常无提示
- `test_tools.py` 扩展（6 个）：三个外部工具失败返回结构化文案、read_file 超限/缺失/目录

**第一次跑分：6 failed**——而且 6 个全是**测试自己写错**，被测代码一行没动：

| 测试错误 | 根因 | 教训 |
|---|---|---|
| 断言 `should_continue(...) == "END"` 失败，实际是 `"__end__"` | 我**凭印象**认为 LangGraph 的 END 常量值是字符串 `"END"`——实际是 `"__end__"`（内部哨兵值） | 断言之前先读库——`from langgraph.graph import END`，断言与常量比较，而不是与猜的字面量比较 |
| `_ainvoke_with_retry` 返回 coroutine 而不是结果 | **async 函数忘了 await**——tenacity 装饰 async 函数后仍然是 async | 被测函数是 async 时，测试函数也要 async（`await` 结果） |
| 正常回复测试 texts == `[]` | FakeGraph 流里**漏放了 `ToolMessage`**——真实链路里工具调用后必有 ToolMessage 复位 `tool_phase`，我的 mock 流里没有，导致后续所有文本被"工具阶段抑制"误杀 | mock 的"剧本"必须还原真实事件顺序，否则被测代码被冤枉 |

**为什么在意：** 这 6 个失败和短板③的两个失败是同一类问题——**测试代码也是代码，同样要"先读后写、不凭猜测"**。特别是"END 常量值是 `__end__`"——如果我没有跑测试直接声称"写好了"，这个错误就会带进 CI 红一次。

**类比：** 裁判（测试）拿着错误的规则书（臆测的 END 值）判罚，运动员（被测代码）白跑一趟。

## 3. 整个过程的思维模式（比代码更重要）

```
先读现状      （工具级容错已有——文档写的"现状"过时了, 别重复施工）
  ↓
四层各司其职  （循环上限防失控 / 重试防抖动 / 防幻觉防撒谎 / 文件上限防卡死）
  ↓
错误让 LLM 决策 （工具失败返回结构化信息, 不替 LLM 做决定, 但压住它编造的冲动）
  ↓
测试也先读库  （END 是 "__end__" 不是 "END"; async 要 await; mock 剧本要还原真实时序）
  ↓
数字收尾      （84 过 / 77% / ruff 零错误）
```

这套打法的通用性：**任何 Agent 工程的四类容错**——失控（循环上限）、抖动（重试）、撒谎（防幻觉）、卡死（资源上限）——都能按这四层往里套，每层都能讲设计理由。

## 4. 概念词典（按出现顺序速查）

| 概念 | 一句话解释 | 类比 |
|---|---|---|
| **工具循环（tool loop）** | Agent 反复"调工具→看结果→再调"的循环，是 ReAct 模式的核心 | 采购员反复打电话确认 |
| **循环上限（MAX_TOOL_ROUNDS）** | 限制 agent 节点最大执行轮数，超限强制结束 | 电话客服的限时 |
| **指数退避（exponential backoff）** | 重试间隔按 1s、2s、4s… 递增，避免在限流恢复前猛试 | 打不通电话越等越久再拨 |
| **reraise** | 重试耗尽后把最后一次异常原样抛出，不吞掉 | 3 次不通就如实说"打不通" |
| **防幻觉指令** | 错误文案里显式告诉 LLM"不要编造" | 紧箍咒 |
| **结构化错误** | 带统一前缀（[工具执行失败]）的错误信息，LLM 能识别"这是失败" | 红色警报灯 |
| **防御性输出** | 宁可少说不可乱说；无法完成时明确告知而不是沉默 | 不懂装懂 vs 老实说不懂 |
| **mock 剧本** | 测试里模拟的事件序列，必须还原真实时序（含 ToolMessage） | 替身演员按真实剧本走位 |

## 5. 下一步（接短板⑤：可观测性）

容错解决的是"失败时怎么办"，但还留着一个问题：**失败时你知不知道？**

- 现在 Agent 链路只有 `print()` 日志，没有 request_id、没有阶段耗时
- 排查"这次回答慢是检索慢了 2 秒，还是 LLM 推理慢了 5 秒"没有任何依据
- `config.py` 里的 `JSONFormatter`/`setup_logging()` 已经写好但 Agent 链路完全没用上

短板⑤ 的路线（详见 `text/interview/面试准备与项目补全指南.md`）：
1. `run_agent_stream` 每个环节埋点：prompt 拼装 / Chroma 检索 / skill 匹配 / LLM 调用（含重试次数）/ 工具执行，统一输出 JSON 日志带耗时
2. `request_id` 贯穿一次完整对话
3. 测试断言 caplog 里包含各阶段日志
