# 代码审查

## 两个审查轴

### 轴 1：规范审查

检查代码是否遵循项目的编码规范：

- **命名一致性** — 变量/函数/文件名遵循项目约定
- **设计 token 使用** — 视觉值从 `:root` CSS 变量引用，无硬编码颜色/间距
- **依赖方向** — 上层依赖下层，无循环引用
- **模块边界** — 跨模块通信走 EventBus/pub-sub，无直接跨层 import
- **类型安全** — TypeScript strict 模式，Python type hints

### 轴 2：实现审查

检查代码是否忠实实现了 spec/PRD：

- 每个 spec 条目是否有对应的代码
- 边界条件是否覆盖
- 错误处理是否完整

## 反模式清单

审查时逐项检查以下常见陷阱：

### "设为 0" ≠ "恢复默认"
- 3D/2D 模型的参数默认值由设计师在数据文件中定义
- 0 往往不是默认值（如眼睛中性值 = 1.0，0 = 闭眼）
- **检查**：代码中有没有 `setParam(x, 0)` 意图"重置"的地方？
- **正确做法**：保存初始快照，恢复时用 `loadParameters()` 或显式设置各参数正确默认值

### intensity × neutral = 语义错误
- 中性状态不应该做强度缩放
- "50% 中性"没有意义
- **检查**：intensity 是否被错误地应用到 neutral 表情？

### 多系统时间不对齐
- 多个系统（表情预设 + 参数 lerp + 动画帧）驱动同一目标时，效果不能瞬时拆分
- Instant preset + smooth lerp = 视觉分裂
- **检查**：驱动同一对象的多个系统是否时间对齐？

### 同一帧内状态变更 + 条件检查 = 竞态
- 清空标志后立即检查"是否已清空"——经典陷阱
- **检查**：`update()` 循环中，状态变更和依赖该状态的条件检查的顺序是否安全？
- **正确做法**：先检查"是否还有工作未完成"，再做清理

### LLM 输出直接消费
- LLM 输出含 emoji/符号/action tag → 直接传给 TTS 会读成乱码
- **检查**：LLM 输出 → 下游消费之间有无过滤管道？

### ref 直连绕过 React state
- `ref.setXxx()` 不会触发 state 更新，任何依赖 state 的 effect 被 bypass
- **检查**：ref 调用是否会导致 React 状态不一致？

### 硬编码参数名
- "这个 SDK 的参数应该叫 XXX" → 实际可能叫 YYY
- **检查**：所有外部数据的字段引用是否已对照真实数据源验证？

## 步骤

1. **明确审查基线** — 从哪个 commit/tag 开始 diff？审查范围是什么？
2. **跑轴 1（规范）** — 逐文件检查命名/风格/架构
3. **跑轴 2（实现）** — 对照 spec 逐项验证
4. **过反模式清单** — 逐一检查上述 7 个反模式
5. **输出审查报告** — 问题列表 + 严重程度 + 修复建议

## 审查粒度

- **必须修**（blocker）：逻辑错误、安全漏洞、数据损坏风险
- **应该修**（warning）：反模式、性能问题、可维护性隐患
- **建议修**（info）：命名优化、注释补充、代码风格
