# 测试驱动开发

TDD is the red → green loop: write a failing test → write minimal code to pass → refactor.

## 步骤

1. **红** — 写一个会失败的测试，只测一个行为
2. **绿** — 用最少的代码让测试通过，不做多余的事
3. **重复** — 下一个测试 → 下一个实现，每个循环一个垂直切片
4. **审** — 全部切片完成后，跑完整测试套件，用 `/code-review` 审查

## 什么是好测试

- 测试**行为**而非实现细节
- 通过公共接口验证
- 读起来像规格说明："用户可以用有效购物车结算"
- 重构时测试不改——因为行为没变

## 测试边界（Seam）

测试应该放在公共接口处，而不是内部实现。

**只测试预定义的边界。** 写任何测试之前，先列出测试边界并确认。不能什么都测——确认边界是为了确保测试精力花在关键路径和复杂逻辑上。

## 反模式

- **实现耦合** — mock 内部协作者、测试私有方法、通过旁路验证（查数据库而不是用接口）
- **同义反复** — 断言用代码的同样方式计算期望值，永远不会失败
- **水平切片** — 先写全部测试再全部实现。测试的是想象的行为而非真实行为

## 循环规则

- **先红后绿** — 先写失败的测试，再写刚好通过的代码
- **逐个切片** — 每个循环：一个边界 → 一个测试 → 一个最小实现
- **垂直切片** — 一个测试 → 一段实现 → 下一个测试。每个切片响应上一轮学到的东西

## 工具使用

- 写测试前跑一遍现有测试，确认基线通过
- 每个测试文件写完就跑，不要堆到最后
- 完整测试套件在提交前跑一次
