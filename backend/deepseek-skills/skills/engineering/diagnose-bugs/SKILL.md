# Bug 诊断

**原则**：Bug 不是靠灵感修好的，是靠缩小范围、排除外因、逐层验证的系统流程。

## 步骤

### Phase 1：复现 → 最小化

1. **精确复现步骤** — 写下触发 bug 的精确操作序列，确保每次都能复现
2. **排除外因** — 关闭无关功能，确认 bug 仍然存在
3. **最小化触发条件** — 砍掉一切不影响复现的步骤，得到最短触发路径

### Phase 2：逐层验证

按**依赖方向从下往上**排查，而不是从头开始乱看：

```
正确排查顺序:
  1. 数据源是否正常？（文件存在？内容正确？）
  2. 底层模块是否正常？（单测通过？手动调用验证？）
  3. 中间层是否正常？（数据传递正确？状态变更正确？）
  4. 顶层是否正常？（UI 渲染？API 响应？）

错误排查顺序:
  从 UI 表现反推 → 猜测后端 bug → 改后端 → 发现是数据源问题 → 回滚
```

### Phase 3：对照参考实现

- 使用第三方 SDK 时 → 对照官方 Sample **完整流程**，不只是初始化代码，要追溯每帧/每次调用的完整链
- 使用框架时 → 对照官方文档的推荐模式
- **关键**：官方 Sample 的 `update()` 调用链比 `init()` 更重要——参数错误在渲染之前就已产生

### Phase 4：假设 → 验证

每个排查动作必须是**可证伪的**：

```
好的排查:
  "如果 Physics 没加载，重影应该还在 → 加载 Physics → 重影消失 ✓"
  "如果参数名不匹配，换正确名字应该正常 → 换名 → 正常 ✓"

坏的排查:
  "我觉得可能是渲染的问题 → 改了渲染代码 → 没效果 → 不知道"
```

### Phase 5：修复 → 回归测试

1. 修复根因（不是症状）
2. 写回归测试（确保不会再犯）
3. 记录经验文档（触发条件 → 根因 → 修复 → 预防）

## Bug 分类排查指南

### 多系统交互类 Bug（如 Live2D 渲染异常）

1. 确认每个子系统的独立状态（Expression 正常？Physics 加载了？Pose 生效了？）
2. 画出数据流 → 在每个交接点加日志 → 找到断裂点
3. **对照官方 Sample 的完整管线**，逐项比对缺失

### 竞态/时序类 Bug

1. 检查状态变更和条件检查是否在**同一帧/同一事件循环**中
2. 检查异步回调的时序（两个回调谁先触发？）
3. **同一帧内先改状态再检查该状态 = 经典陷阱**

### 假设错误类 Bug

1. 列出代码中所有外部数据的引用（参数名、索引、默认值）
2. 逐一对照数据源验证
3. 任何"我以为……"的地方都是潜在的 bug 窝点

## 反模式

- **改症状不改根因** — "加个 `setTimeout` 等 100ms 就好了" → 隐藏了真正的时序问题
- **跳过外因排除** — 没确认是不是自己代码的问题就开始改
- **对照 Sample 只看 init 不看 update** — 最隐蔽的 bug 藏在调用链末端
- **"修好了，虽然不知道为什么"** — 下次还会出现，而且更难排查

## 实战案例

### 同帧竞态：Live2D 表情 Phase 2 目标被清空
- **症状**：所有非 neutral 表情完全失效
- **排查**：加日志追踪 `update()` 每帧的参数变化
- **发现**：Phase 2 trigger 在同一帧内把 `_phaseTwo` 置 null，紧接着 expression check 用 `!_phaseTwo` 判断"过渡完成" → 误判
- **修复**：交换两个检查的顺序——清理检查必须在 Phase 2 触发之前

### 完整调用链：模型重影
- **症状**：模型像两个重叠
- **排除**：不是双实例、不是 alpha 问题、不是驱动代码
- **对比**：官方 Sample 的 `update()` 有 `CubismUpdateScheduler.onLateUpdate()`，我们的没有
- **修复**：补全 Physics + Pose + Scheduler 管线

## 适用场景

- 涉及多个子系统交互的复杂 bug
- 使用第三方 SDK 时出现的异常
- 偶发性/时序相关的 bug
- 任何超过 30 分钟没解决的 bug → 此时应该停下，走系统流程，而不是继续猜
