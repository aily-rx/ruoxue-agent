# 模块设计

设计**深模块**：大量行为藏在小型接口后面，放在干净的边界上，通过接口可测试。

## 步骤

1. **找边界** — 这个功能的调用者是谁？他们需要知道什么？
2. **设计接口** — 最少的参数、最少的返回类型、最少的异常路径
3. **验证接口** — 用"删除测试"试想：删掉这个模块，复杂性去了哪？
4. **实现** — 藏在接口后面的逻辑可以随时重构，只要接口不变

## 核心概念

**模块** — 任何有接口和实现的东西。函数、类、包都可以是模块。
**接口** — 调用者使用模块需要知道的一切：类型签名 + 不变量 + 排序约束 + 错误模式。
**深度** — 接口的杠杆率：调用者每学会一单位接口能调动的行为量。

```
深模块 = 小接口 + 大实现:
┌─────────────────────┐
│   Small Interface   │  ← 少量方法，简单参数
├─────────────────────┤
│  Deep Implementation│  ← 复杂逻辑对调用者隐藏
└─────────────────────┘

浅模块 = 大接口 + 小实现 (避免):
┌─────────────────────────────────┐
│       Large Interface           │  ← 大量方法，复杂参数
├─────────────────────────────────┤
│  Thin Implementation            │  ← 只是透传
└─────────────────────────────────┘
```

## 设计原则

- **深度是接口属性，不是实现属性** — 深模块内部可以由小的、可替换的部件组成
- **删除测试** — 想象删除这个模块。如果复杂性消失了=它是透传。如果复杂性散落到 N 个调用者=它在创造价值
- **接口就是测试面** — 调用者和测试跨同一个边界
- **依赖注入** — 接受依赖，不要创建依赖

## 为可测试性设计

```typescript
// 可测试
function processOrder(order, paymentGateway) {}

// 难测试
function processOrder(order) {
  const gateway = new StripeGateway();  // 内部创建依赖
}
```

## 反模式

- **接口就是实现** — 接口暴露了内部数据结构，改实现就得改接口
- **上帝模块** — 一个模块做所有事，调用者无法独立测试任何部分
- **过度抽象** — 只有一个实现的接口不是接口，是多余层
- **循环依赖** — A 依赖 B，B 依赖 A，拆不开也改不动
- **透传层** — 模块不增加任何行为，只是换个名字转发调用

## 依赖方向

```
上层模块 → 下层模块（单向）
核心层只依赖外部库
模块间通信走 EventBus，无直接跨层 import
```
