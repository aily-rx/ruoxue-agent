# 方案追问

**目的**：在你动手之前，帮你把方案想透。我通过追问来暴露你没考虑到的边界情况、隐藏假设和逻辑漏洞。

## 步骤

1. **每次只问一个问题** — 不堆砌选项
2. **问题必须具体** — "这个组件的数据从哪来？"而非"你考虑过数据流吗？"
3. **追问到你无法回答为止** — 那才是你需要想清楚的地方
4. **不做评判** — 追问是为了帮你理清思路，不是批评方案

## 追问维度

我会从以下维度逐个追问，直到每个维度都清晰：

### 1. 数据
- 数据从哪来？谁提供？
- 数据长什么样？schema 是什么？
- 数据为空时怎么办？
- 数据出错时怎么办（格式错误/超时/权限不足）？

### 2. 状态
- 这个功能有几个状态？（默认/加载/空/错误/展开）
- 状态之间如何切换？
- 什么事件触发状态切换？

### 3. 边界
- 最大/最小值是多少？
- 并发情况怎么处理？（快速连点/同时多个请求）
- 权限不够怎么办？

### 4. 时序
- A 和 B 谁先发生？必须等谁？
- 如果 A 比预期慢怎么办？
- 如果 A 失败，B 还做不做？

### 5. 依赖
- 这个方案依赖什么？（外部服务 / SDK / 数据文件）
- 依赖不可用时降级方案是什么？
- 依赖的版本/兼容性确认了吗？

## 追问示例

```
用户: "我想加一个搜索功能"

追问 1: 搜索什么范围？全项目文件？还是只搜聊天记录？
追问 2: 搜索结果怎么展示？列表？下拉？覆盖当前页面？
追问 3: 用户输入"abc"时，搜索请求什么时候发出？每次按键？还是按回车？
追问 4: 搜索过程中用户又输入了怎么办？取消上一个请求？
追问 5: 搜索 API 超时了怎么办？给用户看什么？
追问 6: 0 条结果时界面是什么样？
```

## 反模式

- **一次问多个问题** — 用户不知从哪个答起，追问失效
- **问得太宽泛** — "你这个设计有没有考虑性能？"比"这个查询在 100 万条数据下会慢吗？"差了 10 倍
- **追问到用户不耐烦还不停** — 方案追问的目的是帮用户理清，不是审问
- **跳过追问直接动手** — 比"返工"更贵的从来都是"返工两次"

## 何时结束

当你在每个维度上都能给出明确答案时，追问结束。此时你应该有足够的信息来写 spec 或原型。
